# Robots off, LinkedIn company pages, privacy exclusion: fetcher change (owner rulings 2026-11-24 and 2026-11-25)

Non-data PR. Changes `scripts/site_corpus.py` (plus its unit tests, `docs/ACQUISITION.md`, `DECISIONS.md`, `tasks/QUEUE.md`). No file under `data/`.
The Chrome retry for bot checks was built, refuted twice, and taken out by the owner's "Split it" (2026-11-25 06:08). It waits for its own PR.

## What this PR does

- **robots.txt is read, not obeyed.** Crawl-delay and the per-host clock stay. Each receipt gets `robots_disallowed`: `yes` if any redirect hop's URL was disallowed, else `unreadable` if any hop's robots.txt could not be read, else `no`. robots.txt receipts carry an empty value; receipts cached before the change read back as `not_recorded`. An unreadable robots.txt is no longer Disallow all.
- **Stale receipts.** A cached `ROBOTS_BLOCKED` or `DOMAIN_BLOCKED` receipt is a cache miss and is refetched.
- **Bot checks go to a person.** A 200, 403, 503 or 999 response that `challenged()` calls a bot-check page (title or wall text, or a widget marker on a refusal code or a nearly empty page) is receipted `BOT_CHECK_MANUAL`, never `ok`, and its URL goes to `manual-bot-check.csv` in the cache folder. A Jina reader result goes through the same test (its `Title:` line and text, plus a short page that says captcha, verify or security check), so a reader-served bot check is `BOT_CHECK_MANUAL` too.
- **Privacy exclusion before any body is stored.** `save()` drops the body of a staff-directory path (`/team`, `/staff`, `/our-team` ...) or a form-only page (fewer than 80 words outside forms), at every status. An `ok` page becomes `CONTACT_FORM_OR_STAFF_DIRECTORY`; other statuses keep theirs with an empty body. A direct body that is excluded is never forwarded to Jina, whatever its HTTP status. Same tests as the 2026-11-16 crawl. A robots.txt body is never written to disk, whatever it holds (owner ruling 2026-11-25 06:43): `Corpus.robots_rules` parses it in memory (once per host per process) and stores only a receipt, `robots-<key>.json` (url, final_url, status, http_status, bytes, sha256, fetched_at). There is no HTML or BOM test any more. Side effect: `rawcheck` on such a page returns `unfetchable`.
- **A LinkedIn company page is never stored; only an allowlisted extract is** (owner ruling 2026-11-25 06:32, "Allowlist, last pass"). `LinkedinExtract` (stdlib `HTMLParser`) keeps the labelled `about-us__*` fields of the page (description, website, industry, company size, headquarters, founded, **specialties**) and, from a JSON-LD Organization, name, description, founding date and a flat address (five scalar keys). Every nested object, employee, post, script and all markup is dropped. The stored file is that extract as JSON (a few KB), the receipt hashes it and records the source URL and fetch time. A page with no name and no field (a wall, an error, changed markup) is `FETCH_FAILED` with nothing stored; a LinkedIn page at any other status stores no body. Tested on the 122 earlier LinkedIn captures (already stripped once): the extractor finds all 7 page fields where the page has them, specialties on 85. A LinkedIn receipt whose stored file is not an allowlisted JSON extract (a raw company page from before the rule) is a cache miss, never replayed, and its raw, text and receipt files are deleted: on that lookup, and by a sweep of the whole cache the first time a process opens it (owner ruling 2026-11-25 06:43). The LinkedIn commits are separable from the rest of the PR.
- **LinkedIn.** `/company/<slug>` and `/showcase/<slug>`, optionally `/about`, are fetched logged out (curl with `-q`, no cookie jar, no header). Everything else on LinkedIn (`/in/`, `/pub/`, `/company/<slug>/people`, jobs, `lnkd.in`, a Jina-wrapped URL) is refused as `DOMAIN_BLOCKED` at the first URL and at every redirect hop, including a hop from an own site. A redirect to `/authwall`, `/login`, `/uas/` or `/checkpoint` is `SIGNIN_WALL`. LinkedIn never goes through Jina. `linkedin_url()` keeps its meaning, so `check_evidence_binding.py` still refuses LinkedIn as an evidence source (the evidence route is a separate PR).

## Evidence for the follow-up browser PR (not built here)

Measured 2026-11-25 on PR #560 head 5dd966d9 (`Corpus.browser`, since removed), outside the repo, owner-ruled "click through bot checks":

- **Headless real Chrome (Playwright `channel='chrome'`, `headless=True`) does not clear the check.** 3 of 3 LinkedIn company pages tried (Avient, Day-Glo, Vibrantz) came back as Cloudflare's interactive "Just a moment..." challenge (`__cf_chl_rt_tk` in the URL), 403, about 40 s each, all `BOT_CHECK_MANUAL`. curl got the same Cloudflare 403.

All 127 LinkedIn company pages (PIC-18 owners with `linkedin_url`) were then fetched headed: 122 page, 1 sign-in wall, 4 failed, 0 bot checks. So `headless=True` was the yield limit, not the click logic.
