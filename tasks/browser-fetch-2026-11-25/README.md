# Headed Chrome retry for bot checks, HTTP/1.1 transport fallback (owner rulings 2026-11-24 and 2026-11-25)

Non-data PR. Changes `scripts/site_corpus.py` (plus its unit tests, `docs/ACQUISITION.md`, `DECISIONS.md`). No file under `data/`.
Follows #560, which shipped robots off, LinkedIn company pages, privacy exclusion and `BOT_CHECK_MANUAL` without a browser (owner ruling 2026-11-25 06:08, "Split it").

**Headed Chrome opens a window on this Mac** for every bot-check retry (and every real-Chrome case of the check). Windows appear and close on their own; do not click in them. Headless Chrome is held by Cloudflare (3 of 3 LinkedIn pages), headed passes without a click, so the browser is headed on purpose.

## Design (as implemented at the head)

- **One retry, no clicks.** A page the curl path calls a bot check (`challenged()`), a reader-served bot check (Chrome tries the original URL), a `BOT_CHECK_MANUAL` receipt written before this PR (no `browser_tried` mark), or a certificate chain or handshake curl still rejects after the HTTP/1.1 retry, is visited once by `Corpus.browser`: local Playwright, real Chrome (`channel='chrome'`), headed, a fresh non-persistent context, no profile. No click and no typing: the code has no click path. It waits up to 30 s for the page's own check and stops at once if the navigation itself fails.
- **Chrome missing is its own outcome.** Playwright or Chrome unavailable gives `BROWSER_UNAVAILABLE` (error says which), replayed from the cache like any receipt: a second fetch makes no new network attempt and adds no second row to `manual-bot-check.csv`. A bot-check page whose browser run ran and stayed a check is `BOT_CHECK_MANUAL` with `browser_tried: yes`.
- **A layered request boundary, with what each layer is proven to stop.** (1) `Worker` and `SharedWorker` do not exist in the page (an init script on every frame), so no worker target can be created from it; frames are never admitted (only main-frame documents are) and popups are blocked by `--block-new-web-contents`. (2) A context-level Playwright route (`BROWSER_DENY`) aborts everything except the guarded page's main-frame navigation on every target Playwright attaches. (3) The guarded page's CDP session pauses each request at the Fetch request stage, redirect hops included (Playwright routes do not see them), and `Corpus.guard` decides it. (4) A browser-level target watch (`Target.setDiscoverTargets`) fails the visit, keeping nothing, if Chrome creates any target type other than the page, its tab or Chrome's own UI (a worker, shared worker, service worker or other target), and a second page fails it too. This is detection after creation, so layers 1 to 3 are what keep a request off the wire. Proven by the check on the local fixture: popups, child frames, dedicated and shared workers. For the two worker kinds the check also runs a control with layers 1 to 3 off and shows both requests then arrive at the server. Not proven: other target types (the target watch aborts them but no fixture creates one), service workers (blocked by the context option, not exercised), and anything on a real site.
- **What the guard decides for each main-frame document:** refused LinkedIn URLs (`/in/`, `/pub/`, `/company/<slug>/people`, a hop from an own site) and staff-directory paths are failed before they are sent, a `/robots.txt` document is refused (receipt-only on every route), and another host is admitted only as an HTTP redirect hop. Each admitted hop reads that host's robots.txt (in memory), records its state, and waits that host's clock with its own Crawl-delay (`Corpus.wait_host`). A response's Retry-After, in delta-seconds or HTTP-date form with no cap, books the same shared host clock as an absolute deadline (never earlier than the server's date) (curl's transport reads both forms too). `robots_disallowed` is yes, unreadable or no across the curl hops, every browser hop and the final URL.
- **No cookie is ever sent.** Set-Cookie is stripped from every response, the jar is emptied before every request, a Cookie header is stripped from every request, and `document.cookie` is a no-op. The fixture sets cookies in a redirect, a response and JavaScript, and its server never receives a Cookie header; a control run shows an unprotected Chrome does send one.
- **What is stored.** Storage is decided after the final classification: only an `ok` main document (final HTTP 200, not a bot check, no replacement character) is stored; no non-ok status keeps a body; a bot-check page, error page or refused hop is never stored. Excluded destinations stay excluded by `save()`, and a LinkedIn page is reduced to the allowlisted JSON extract, as on main. The browser takes slots from its own two-slot pool and none from the curl pool, so the robots lookups it triggers cannot deadlock on a curl slot.
- **Transport fallback.** Inside each hop's transport step (page, redirect hop or robots.txt), a curl exit 35 (handshake), 60 (certificate chain) or 92 (HTTP/2 stream), whatever HTTP status curl had read, gets one retry over `--http1.1`, and its response, redirects included, is processed normally. Certificate verification stays on (the check asserts no `-k`).
- **Cache index.** A change of the receipt columns rewrites `index.csv` and any older `index-robots.csv` by named columns before a row is appended: into a temp file, verified (row count and width), then `os.replace`d over the index, so a failure leaves the original byte for byte. A row as wide as the current header under an older header keeps its columns (`browser_tried` included); a row of any other width raises and leaves the index unchanged. Every row then has the header's width and `browser_tried` is a named column.

## Measured on real sites (2026-11-25, round-1 head)

- 3 of 3 LinkedIn company pages (Avient, Day-Glo, Vibrantz) read: curl got Cloudflare's 403, the headed retry returned the page, the receipt is the allowlisted extract (robots.txt says Disallow for that path, so `robots_disallowed` is yes). 3.7 to 5.4 s each.
- The own-site failures counted on main did not mostly yield. `www.may-lin.com` and `premieraerosol.com` (curl 60): Chrome also refuses them (`ERR_CERT_COMMON_NAME_INVALID`), the host name is not on the certificate, so `FETCH_FAILED` is right. `molding-dynamics.net` (curl 35): Chrome fails too (`ERR_SSL_PROTOCOL_ERROR`). `mercurymachine.com` and `www.bmsburns.com` (curl 92 in the main run): with the declared crawler user agent curl now gets exit 52 (empty reply) over HTTP/1.1 as well, while a bare `curl` without that user agent gets 200: those sites drop the declared agent, which no transport retry changes. Count these as results, not as yield of the fallback.
