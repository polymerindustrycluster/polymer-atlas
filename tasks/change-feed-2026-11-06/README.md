## Result and reproduction

Run `git fetch origin main`, then `python3 scripts/build_changelog.py` (default local origin/main), or `python3 scripts/build_changelog.py --ref main` in a full local main checkout. Generates only `build/changelog/CHANGELOG.md` and `build/changelog/feed.xml`. Outputs are uncommitted, derived artifacts. Ref resolves once to a commit before traversal; working/index/unmerged branch changes are excluded. A shallow clone fails before writing output; fetch complete history first.

The unit is distinct keyed record rows or existing-key field changes at each first-parent main update, never companies or operating impact. One entry per main commit touching a supported data CSV: standard merge/squash PR subjects supply the PR number; unmarked historical main commits are labelled by commit without inventing a PR. Feature-branch intermediate commits are not separately counted. New evidence is counted by target record_table and first-seen EVD ID, not duplicated in record-creation lists. Existing-key status and verification_tier transitions include blank values. Previously seen keys returning after a loss are restorations, not first-time creations; removals are separately labelled so historical losses/restorations do not inflate new-record counts. Notes-only data commits honestly report zero changes in these categories; other field edits are outside this feed.

Records created are listed by ID, with table and row counts. Registry/person links use their composite grain; multiple links share the owner ID label with an explicit row multiplicity. No registry identifier text is printed. Archive links are one-per-evidence_id, per §4.22. Shards are unioned; reorder/CRLF and shard migrations preserve keys. The early history contains ORG000101–103 simultaneously in organizations and ecosystem with differing tiers. Under AGENTS §3's false-merge caution, these table-specific historical rows stay distinct; cross-table transfer matching requires an ID unique on both sides. This is a counting policy, not a data/entity-resolution edit.

## Privacy and trust boundaries

The output allowlist is immutable record IDs, fixed table labels, counts, controlled status/tier values, Git commit timestamps/SHAs and PR numbers. No record names, addresses, notes, source/claim descriptions, registry identifier strings, commit subjects/bodies/authors, branch names or contacts are copied. Unknown historical status/tier values are rendered `(unrecognized)`; their changes are still counted. IDs are structurally checked, and required key columns must exist. Malformed CSV, conflicting duplicate public projections, unsupported data tables/evidence targets, shallow history or an output symlink escaping build/ stop generation before replacing artifacts. inclusion_log and generated *_all exports are explicitly excluded. Identical repeated keys are counted once; counts represent distinct keys.

No existing changelog/Atom generator was found by searching scripts/*.py. The proposed `scripts/check_row_loss.py` is not on main; its implementation was read from origin/agent/claude-code/row-loss-guard. This script follows its shard normalization and registry/person link grain without importing an unmerged branch or creating a shared framework. Stdlib csv, subprocess and ElementTree handle parsing/Git/XML. Atom metadata/content follows [RFC4287 §§4.1.1–4.1.3](https://www.rfc-editor.org/rfc/rfc4287#section-4.1.1); content is plain text with namespace, stable IDs, titles, timestamps and feed author, serialized as XML.
