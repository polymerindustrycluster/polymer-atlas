## What a source has to contain to name a process
The pages read here name **products and markets, not methods**: "we supply…", "for the automotive industry", a product catalogue, a brand list. Of 18 readable organizations one states a process of its own in a sentence (MSB: "can produce any type of mold"); two more state one only through a parent's technology claim or an equipment maker's service line, which are held on rulings. A source that can settle process therefore has to be (a) about the establishment, not the group, (b) in the vocabulary of operations, naming what is done to the material (molds, extrudes, compounds, thermoforms, vulcanizes, coats), and (c) written by or for a regulator or auditor, not a marketer: an air, wastewater or hazardous-waste permit that lists emission units, an equipment or production-line listing, a customer or supplier technical-data sheet that states the process, a plant tour or a capability statement that an engineer wrote. Marketing pages state it only by accident. The next route should be chosen on those three properties; I did not test any other source.

## Method as run
`fetch.py`: record website, then up to 5 same-registrable-domain pages chosen from the **home page's** links by link text/path (capabilities, process, what we do/manufacturing, services, industries/markets/applications, products/solutions, about, in that order), direct curl (no proxy, no sitemap guess), robots.txt per host gated every hop, 1.2 s between requests per host, one retry only after a curl transport failure, no retry on any HTTP status. Captures (raw bytes, extracted main text with line kinds, sha256) are in `S/persist/web-canary-2026-11-22/`, outside the repo. Main text = visible text minus nav, header, footer, aside, form, script and menu-like class wrappers (with a tag-only fallback when a wrapper swallowed everything; flagged in `note`).
Deviations, stated plainly:
- **Pass 2:** the first run did not follow redirects when reading robots.txt, so 5 organizations showed ROBOTS_UNREADABLE for a defect of mine; fixed and re-run (their pass-1 rows stay in `fetches.csv`, labelled pass 1). Two of the 5 are still unavailable on the corrected run (timeout; robots disallow).
- **Pass 3:** CF Extrusion's home page is a meta-refresh to `/site/` on the same domain; it was treated as a redirect hop of the record URL (target fetched, then 5 links chosen from it), so the cap of the record URL plus 5 pages holds; the thin home page row and the six pages after it are all in `fetches.csv` pass 3.
- robots.txt bodies and non-200 response bodies (403, 202) were hashed, not stored (`check.py` exempts them); readable and thin page captures are all stored. A few pages (e.g. AlphaMicron industries) were fetched under two URLs and are the same text.
- **Pass 4 (controller instruction, 2026-11-22):** on a transport failure the fetcher now retries once over `--http1.1` with the same declared user-agent (robots.txt still governs), and what remains is classified (`NO_DNS` exit 6, `CONN_REFUSED` 7, `TIMEOUT` 28, `TLS_ERROR` 35/60, `EMPTY_REPLY` 52, `HTTP2_ERROR` 92, HTTP 404 on the home page, thin page). The 7 unreadable organizations were re-run: **none was rescued.** Buckeye Rubber still answers an empty reply (52) over HTTP/1.1; Custom Pultrusions redirects to the www host and times out; Solutions in Polycarbonate fails TLS (60); Eurotech HTTP 403; RealTruck HTTP 202 empty; Sietins robots.txt disallows; SKF is script-rendered. **No no-DNS and no home-404 site occurred**, so `record_health_leads.csv` has a header and no rows. `wayback.csv` records only whether the Wayback availability API lists a capture and its date for each of the 7 (6 have one, dated 2022-05 to 2026-11; Custom Pultrusions has none); no archived page was read or cited, and whether an archived copy may serve as a source is with the owner.

## What a cheaper model could do, and what needs judgement
- **Cheaper-model steps, no loss:** frame draw (`frame.py`), fetching and storing (`fetch.py`), text extraction, the keyword screen (`screen.py`), offsets and hashes (`build_candidates.py`, `check.py`). These were roughly 40% of the effort (estimate) and are deterministic; the fetch run needed two code fixes caused by my own defects (robots redirect, meta refresh), which a tested fetcher would have avoided.

A cheaper model would likely over-fill from list items and parent pages; a screen-only run would have missed MSB's about page (the 2B lane screened this organization and found nothing).
